# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**tribbu** is a school-community ("comunidad escolar") mobile/web app: parents (apoderados), Room Parents (admins) and a Super Admin coordinate per-classroom (`curso`) life — calendar, lunch menu, birthdays, reminders, fundraisers (colectas), contacts, etc. React + Vite SPA, Supabase backend, packaged as an Android app via Capacitor + OneSignal push. The domain and all UI copy are in Spanish — match that when writing new strings.

## Commands

```bash
npm run dev       # Vite dev server (web)
npm run build     # production build to dist/
npm run preview   # serve the built dist/
npm run lint      # ESLint (flat config in eslint.config.js)
```

There is **no test suite** and no test runner configured. `npm run lint` is the only automated check. Web lint is at **0 errors** (2026-09-23) and CI (`.github/workflows/ci.yml`: web build + lint, mobile lint + Metro bundle) blocks on errors; the ~45 remaining **warnings** are the app-wide `useEffect(()=>{ cargar() },[...])` data-loading pattern (`react-hooks/set-state-in-effect` downgraded to warn + `exhaustive-deps`) — converting those loaders to `useCallback` is a separate refactor. Keep new code error-free.

Android (Capacitor wraps the built `dist/`):
```bash
npm run build && npx cap sync android   # rebuild web + copy into android/
npx cap open android                    # open in Android Studio
```

## Environment

Copy `.env.example` to `.env`. Required: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`. Also referenced in code: `VITE_ONESIGNAL_APP_ID` (push). The client only ever uses the **anon** key; the service-role key must never appear in `src/`.

## Architecture

### App shell — `src/App.jsx`
**Code-splitting (2026-09-25):** every feature tab (and `SuperAdmin`, `BusquedaGlobal`) is `React.lazy`-loaded through the `aLazy()` helper at the top of `App.jsx`, with `<Suspense fallback={<Spinner/>}>` around `renderTab()` and the Super Admin screen — the initial bundle went from ~1.35 MB to ~470 KB. `xlsx` is never imported statically: the four places that use it do `const XLSX = await import("xlsx")` inside the export/import handler. Keep new features lazy and new heavy libs dynamic.
A single ~520-line component that owns nearly all top-level state and routing. There is no router library; `tab` state drives a `switch` in `renderTab()` that mounts one feature. Since 2026-09-23 `tab` is mirrored in the URL as `?tab=<id>` (no param = `muro`) via `history.pushState` + a `popstate` listener, so browser back/forward move between tabs and a section link survives login (`tabDeUrl()`/`TABS_VALIDOS` in `App.jsx`). Query, not hash — the hash belongs to the password-recovery link. `?tab=admin` without `isAdmin` renders the Muro. Super Admin's own sections are not URL-synced. Key responsibilities:
- **Session bootstrap**: on mount, `supabase.auth.getSession()` → load the `usuarios` row (joined with `usuario_hijos` + `usuario_cursos`) by `auth_id`, shape it into the `usuario` object.
- **"Mi acceso" model**: `items` = the user's children (`hijos`) plus any courses where they are a Room Parent. `cursoIdx` selects the active item; `rolEfectivo` ("padre" | "admin") is derived per-item — **a user can be a parent in one course and admin in another**. With hijos in more than one curso, a pseudo-item **"Todos"** is prepended (first and the login default): the **global unified view**, mirroring mobile. The contract every feature follows (all passed as props from `App.jsx`): read with `.in("curso_id", cursoIds)` (`cursoIds` = all cursos with hijos in Todos, `[cursoId]` per-hijo, memoized for stable identity); `esVistaTodos` bool; `cursoId` **null** in Todos; `isAdmin` false in Todos; `tagDeCurso(curso_id)` → `{nombre, color}` only in Todos, used to tag rows (8px identity-color dot + first name); writes use the entity's `curso_id`, never the session `cursoId`. Single-curso users see zero change. Spec: `specs/vista-unificada-hijos-mobile.md`.
- **Three layouts** rendered from the same state: Super Admin (`usuario.rol==="super"` → only `<SuperAdmin/>`), mobile (bottom tab bar + "Más" menu), and desktop (fixed sidebar). When changing navigation/header, update all three.
- **Super Admin's own navigation** (`src/features/superadmin/index.jsx`): its 11 modules (Usuarios/Cursos/Promoción/Maestros/Alumnos/Horarios/Uniformes/Colegio/Alertas/Comunicaciones/Menú — "Códigos" removed 2026-09-11 along with self-registration, see Backend & auth below) are grouped into 4 categories (Personas/Cursos/Comunidad/Colegio, `SECCIONES` const) and rendered as a **left sidebar on desktop width** (≥768px, `useIsMobile()`) — mirroring the main app's own desktop sidebar pattern (dark `#0F172A`, active-item highlight) so Super Admin doesn't feel visually separate from the rest of the app. Below 768px it collapses to the grouped sections stacked with small pill-wrap rows per group, never a fixed-width side column (a 196px sidebar on a phone-width screen squeezes the content column to near-nothing without technically causing page overflow — a real but easy-to-miss regression, checked for explicitly via `document.body.scrollWidth` in the browser). Content lost its `maxWidth:800` cap (now 1200 in `App.jsx`) since the sidebar frees up the width for tables/cards to breathe. Mobile app (`mobile/features/superadmin/index.jsx`) mirrors the same 4 categories as a **module grid home screen** (tap a module → its screen + a "← volver" back button) instead of the old horizontal-scrolling chip strip. Promoción stays web-only; the mobile **Colegio** module is contact-info-only (`ColegioAdmin` — edits the `colegios` row: nombre/teléfono/email/dirección/horarios/sitio/mapa + `logo_url` via `pickAndUploadImage`), without the year-scoping/duplication tools of the web "Cursos" screen. This mobile panel now serves **both** `super` (`isSuper`) and **`colegio_admin`** (`esColegioAdmin` from `useSession()`); routing to it is `isSuper || esColegioAdmin` in `mobile/app/_layout.jsx` (`vaAlPanel`), and the panel branches on `esColegioAdmin` for the header label ("Admin del colegio", amber) and to hide the "◇ Super Admin" toggle in the apoderado create/edit modal (`ocultarAccesoEspecial`). `colegio_admin` scoping is pure RLS (`supabase/multi-colegio.sql`), no client-side `colegio_id` filter — same as the web. See `specs/colegio-admin-en-mobile.md`. **`super` on mobile** (2026-09-23) gets a "COLEGIO" selector at the top of the panel (defaults to the first colegio by `creado_en`) and `cargar()` applies the same client-side `colegio_id` filter as the web (RLS doesn't scope `super`) — before, it mixed every colegio's data and couldn't create cursos. `activeColegioId` (= `miColegioId` for `colegio_admin`) feeds curso creation, `ColegioAdmin`, `UniformesAdmin` (which also stopped failing silently on new categorías: it inserted without the NOT NULL `colegio_id`) and `Comedor`/`UploadMenuExcel` via a new `colegioId` prop. No "Plataforma" section on mobile (creating colegios stays web-only).
- **Push deep-linking**: OneSignal notification clicks dispatch a `tribbu:navigate` CustomEvent; `TAB_MAP` maps notification `type` → tab id. `window._tribbuPendingTab` / `_tribbuUserId` bridge the native plugin and React.

### Features — `src/features/<name>/index.jsx`
Each feature is one self-contained file exporting its component(s) (e.g. `Muro`, `Calendario`, `Finanzas`, `SuperAdmin`). They receive `cursoId`, `userId`, `isAdmin`, etc. as props and do their own Supabase queries directly — there is no shared data/store layer. `features/shared/index.jsx` holds cross-feature widgets (`EmojiPicker`). The canonical `ListToolbar` lives in `src/components/ListToolbar.jsx`. `features/contacto` exports both `Contacto` and `Alumnos`.

### Shared modules
- `src/lib/theme.js` — design tokens (`T` color palette, `ROL_LABEL`/`ROL_COLOR`, `HIJO_COLORS_CUSTOM`, `MESES`). Import these instead of hardcoding colors. **Pure & cross-platform** — also consumed by the mobile app via the `@shared` alias.
- `src/lib/tokens.js` — the full design-token system layered on `theme.js` (also pure/cross-platform, `@shared/tokens`): `SLATE`/`BLUE` ramps, `STATUS`, **`THEMES.light`/`THEMES.dark`** (same keys; dark = the login/AppHeader recipe), `TYPE`, `SPACE`, `RADIUS`, `SHADOW`, `MIN_TOUCH`, and `withAlpha`/`roleTheme`/`childTheme`. Reference doc: `mobile/DESIGN_SYSTEM.md`. Prefer these over raw hex in new code (web and mobile).
- `src/lib/muro.js` + `src/lib/encuestas.js` (2026-09-23) — the Muro "Pendientes"/cumpleaños rules (`proximoCumple`, `recordatoriosPendientes`, `colectasActivas`/`colectasPendientes`, `festejosPendientes`, `encuestasAbiertas`, `alertasUnaPorCurso`) and the Encuestas rules (`estaCerrada`/`estaEliminada`/`estaActiva`, `resultadoOpcion`, `opcionGanadora`, `MIN/MAX_OPCIONES`), shared by web and mobile (`@shared/muro`, `@shared/encuestas`). Pure (no supabase): each screen does its queries and passes the rows. Put new data-shaping logic for these screens here instead of copying it per platform — the copies had already drifted into real bugs (deleted encuestas in Pendientes on both; past/duplicated festejo invitations on web; several alerts per curso on mobile).
- `src/lib/helpers.js` — pure helpers: `fmtM` (money, es-AR), `fmtF`/`fmtDM` (dates), `dHasta` (days-until), `sanitize`/`safeUrl` (basic XSS guards — use `safeUrl` for any user-supplied link), `getHijoColor`/`setHijoColor`. The color helpers delegate to a **pluggable storage backend** (`src/lib/storage.js`, default `localStorage`) so mobile can back them with AsyncStorage without changing the sync signature.
- `src/lib/runtimeConfig.js` + `src/lib/storage.js` — **platform-injection seams**. `lib` no longer reads `import.meta.env` directly: the web injects config in `src/bootConfig.js` (imported first in `main.jsx`); mobile injects `EXPO_PUBLIC_*` + an AsyncStorage backend. `supabase.js`, `lib/push.js`, `lib/authAdmin.js` read URL/anon from `getRuntimeConfig()` — keep new env reads going through there, not `import.meta.env`.
- `src/hooks/useListControls.js` + `src/components/ListToolbar.jsx` + `Paginador.jsx` — the standard pattern for any searchable/sortable/filtered/paginated list. Wire `const ctrl = useListControls(items, {...})` then `<ListToolbar {...ctrl}/>` and map `ctrl.items`.
- `src/components/` — `Card`, `Pill`, `Spinner`, etc., re-exported via `components/index.js` barrel. `Adjuntos.jsx` (`AdjuntosInput`/`AdjuntosList`, `MAX_ADJUNTOS = 3`) is the attachments pattern for recordatorios/eventos: images + PDFs (10 MB cap, client-validated), uploaded to the **private** `adjuntos` Storage bucket at `{cursoId}/{ts}.{ext}` and persisted as a `jsonb` array of `{url, tipo: "imagen"|"pdf", nombre}` on the row (`url` is now the storage **path**, not a public URL — see Storage buckets below). Mobile mirror: `mobile/components/Adjuntos.jsx`.

### Storage buckets (`supabase/storage-privado.sql`, 2026-09)
`adjuntos` (recordatorio/evento attachments + colegio logos at `colegios/{id}/logo.*`) and `eventos` (festejo invitation images) are **private**: no `getPublicUrl`, every access is signed on render (1 h TTL). `libros` (textbook cover images) stays **public** on purpose. `src/lib/storageUrl.js` (+ `mobile/lib/storageUrl.js`) = `parseStoragePath` / `signStorageUrl`; `src/components/SignedImg.jsx` (`<SignedImg src bucket>` + `useSignedUrl` hook) / `mobile/components/SignedImage.jsx` (`<SignedImage>`) render private images. `parseStoragePath` accepts **both** a bare path (new rows) and an old full `/object/public/<bucket>/…` URL (pre-migration rows) — new uploads store the bare path. `mobile/lib/media.js`'s `pickAndUpload*` return the path for private buckets, the public URL for `libros`. Storage RLS: SELECT for `authenticated` on the private buckets (was: anyone on the internet). **Two old `public`-role read policies ("Allow public read" on eventos, "adjuntos_read") had survived that migration** — found 2026-09-23 (anon key could list/download both buckets) and dropped in `supabase/storage-cerrar-publico.sql`, which also limits "upload libros" to `authenticated`. When touching Storage policies, check `pg_policies.roles`, not just the `qual`. When adding a new place that shows one of these images, use `<SignedImg>`/`<SignedImage>`, never `getPublicUrl`.

### Styling
**All styling is inline `style={{}}` objects** — no CSS modules, no Tailwind, no styled-components (only `index.css`/`App.css` globals exist). Follow the existing inline-style convention and pull colors from `T`.

### Backend & auth
- Auth is **Supabase Auth** (`signInWithPassword`, `resetPasswordForEmail`). The `usuarios` table row is linked by `auth_id`. `bcryptjs` is no longer imported by the app (removed 2026-09-23); the dependency stays only for the one-time root `*.cjs` migration scripts.
- **Self-registration via invitation code — removed 2026-09-11**: apoderados used to be able to sign themselves up with a per-curso code shared by their Room Parent ("Registrarme con código de invitación" on Login, both web and mobile — `RegistroConCodigo` in `features/auth`) or have Super Admin manage those codes ("🔑 Códigos" module, `CodigosInvitacion` in `features/superadmin`, both platforms). All of that UI is gone; apoderado accounts are now created only from Super Admin ("👤 Usuarios" → nuevo apoderado). **Not** touched, on purpose: the RPCs `verificar_codigo`/`crear_apoderado` and the `codigos_invitacion` table (`supabase/rls-hardening.sql`) — nothing in the client calls them anymore, but the table/RLS/functions are left in place rather than dropped. `eliminarCurso`'s cleanup (deletes `codigos_invitacion` rows for a curso being removed, alongside `horarios`/`usuario_cursos`/etc.) is unrelated and was kept.
- **Password recovery** (`specs/recuperacion-de-contrasena-por-email.md`): both web and mobile send `resetPasswordForEmail` with `redirectTo` pointing at the **web** SPA (`WEB_APP_URL` = `https://www.tribbu.ar/app` in `src/lib/appUrl.js`, consumed by mobile as `@shared/appUrl`) — mobile links deliberately complete in the browser, not via a native deep link. The link lands on `/app` with `#…&type=recovery`; `src/supabase.js` sets `detectSessionInUrl:true` + `flowType:"implicit"` explicitly so that hash is processed, and `App.jsx` renders `<NuevaPasswordRecovery/>` (a full-screen recovery view in `features/auth`, above the login/app branches) on the `PASSWORD_RECOVERY` event or a lazy `type=recovery` hash check. After `updateUser({password})` succeeds it clears the hash and reloads → the persisted session logs the user in with no re-login. **Requires manual Supabase config** (Authentication → URL Configuration): Site URL `https://www.tribbu.ar/app` and Redirect URLs allow-list `https://www.tribbu.ar/app` + `https://www.tribbu.ar/app/**` — without it Supabase ignores `redirectTo` and falls back to the (stale) Site URL.
- **Privileged auth operations** (create user, change another user's email/password, find by email) go through the Edge Function `supabase/functions/manage-auth-user/index.ts`, called via `src/lib/authAdmin.js`. The function verifies the caller's `rol` is `super` or `colegio_admin` via JWT before using the service-role key server-side — never `admin` (a Room Parent is `rol="admin"` too but only for their own curso, and this function's `create`/`update`/`find` actions operate on any user in the system with no curso scoping; letting `admin` through here was a real privilege-escalation bug, fixed 2026-08-25). `colegio_admin` (multi-colegio, 2026-09) is scoped inside the function itself (`targetEnColegio()`): it can only `update`/`find` a user who already belongs to its own `colegio_id` (derived the same way as `es_colegio_admin_de_usuario()` in `supabase/multi-colegio.sql`, resolved by hand since the function runs with the service client, no `auth.uid()`); `create` has no target yet so it's unrestricted for both roles. **Never** add the service key to the frontend — route new admin operations through an Edge Function instead. **`find`/`update` self-heal** (fixed 2026-09-10): `listUsers()` used to be called with no pagination, so with >50 Auth users whoever fell past page 1 silently failed to resolve by email; `find` and `update`'s fallback now page through all of Auth (`findAuthIdByEmail()`). `update` also recovers when the caller's stored `auth_id` no longer exists in Auth (deleted manually, or a leftover from the pre-Auth bcrypt migration) — the client now always sends `current_email` (the user's *current* email, not the new one) alongside `auth_id`; on a `updateUserById` "not found" the function retries via `findAuthIdByEmail(current_email)`, or — if truly no Auth account exists — creates a fresh one with the password being set, returning `auth_id_reparado` for the caller to rewrite `usuarios.auth_id`. Before this, "cambiar contraseña" for such a user failed with a raw "User not found" and no recovery path (`src/features/superadmin/index.jsx`'s `guardarUsuario`/`guardarCuentaEspecial`, mirrored in `mobile/features/superadmin/index.jsx`). The "no existe" check is `error.status === 404`, not a text match on `error.message` — a fuzzy `/not found/i` match briefly misfired on `AuthRetryableFetchError` (a transient 5xx that supabase-js explicitly marks "safe to retry"), wrongly triggering account recreation instead of just retrying; `withRetry()` now retries transient 5xx/`AuthRetryableFetchError` responses (300ms/600ms backoff, 3 tries) on every Auth admin call before giving up. When `auth_id` is missing entirely (not stale — never set), the client now falls back to `authAdminCreate` with the password being set, instead of dead-ending on "No se encontró el usuario en Supabase Auth".
- **`instance_id`/`aud` NULL — root cause of ~58 accounts invisible to Auth (found & fixed 2026-09-11)**: rows inserted directly into `auth.users` by the one-time bcrypt→Auth migration scripts (`migrate_to_auth.cjs`/`migrate_remaining.cjs`) left `instance_id` and `aud` `NULL` instead of `00000000-0000-0000-0000-000000000000`/`"authenticated"` (the columns Supabase Auth's own `admin.createUser()` always fills in, but a raw SQL insert doesn't). Auth filters **every** admin-API query by `instance_id` — a `NULL` never matches, so those accounts were 100% valid rows (right email, right password hash, right `usuario_hijos`/`usuario_cursos`) yet totally invisible to `listUsers`, `getUserById`, `updateUserById`, and the dashboard's own Users list, while still showing up fine in a direct SQL query — the exact "some accounts work, some don't, always the same ones" symptom that made this hard to place (surfaced as "Database error checking email" from `updateUserById`). Fixed with one manual `update auth.users set instance_id = '00000000-0000-0000-0000-000000000000', aud = coalesce(aud,'authenticated'), role = coalesce(role,'authenticated') where instance_id is null or aud is null or role is null;` (ran once against prod, no migration file committed for it). Any account created by directly writing to `auth.users` again (instead of through `admin.createUser`/`auth.signUp`) will reintroduce this — diagnose the same way: compare a working account's `auth.users` row against a broken one's, `instance_id`/`aud` are the columns that matter.
- **`UploadApoderadosExcel` (bulk import, both platforms) silently created apoderados with no Auth account** (fixed 2026-09-11): if `authAdminCreate` threw for a row (rate limits during a big batch are the likely trigger), the error was only `console.error`'d — the `usuarios` row was inserted anyway with `auth_id: null`, and the row still counted toward the "✅ N apoderados procesados correctamente" success count, so a silently-broken account was indistinguishable from a working one until someone tried to log in. Now collects the failed emails into `sinAuth` and appends them to the completion message so the admin knows exactly who to fix.
- **Self-service account deletion** (Apple 5.1.1(v)) — Edge Function `supabase/functions/delete-account/index.ts`: no role required, the caller's JWT is the only account it can delete. Removes the user's own rows (push_tokens, leídos, asistencias, adquiridos, personal recordatorios, usuario_cursos/usuario_hijos, `usuarios` + Auth user), nulls historical refs (colecta_pagos.pagado_por, colectas/cumples responsable_id) and never touches `hijos`; `super` is refused. Mobile UI: "Eliminar mi cuenta" in Más → Cuenta (`mobile/app/(tabs)/mas.jsx` + `deleteMyAccount` in `mobile/lib/authAdmin.js`); web: `EliminarCuentaModal` (`features/auth`), opened from the account actions in both web layouts of `App.jsx`.
- **Push** is sent via the `send-push` Edge Function (`supabase/functions/send-push/index.ts`) called from `src/lib/push.js` (`sendPush`, `getUserIdsByCurso`) — the single source for push helpers, imported by every feature as `../../lib/push`. It resolves recipients' Expo push tokens from `push_tokens` and posts to the Expo Push API (replacing the old OneSignal sender); invalid tokens (`DeviceNotRegistered`) are pruned. Requires a real logged-in user's JWT as bearer (no super/admin role check — any apoderado triggers push today, e.g. creating a recordatorio) — `sendPush` sends `session.access_token`, **not** the anon key; calling with just the anon key (no real user) is rejected with 401 (fixed 2026-08-25, was previously callable by anyone holding the — public — anon key, no account needed).
- **Automatic push (avisos automáticos, 2026-09-23)** — Edge Function `supabase/functions/avisos-automaticos/index.ts`, deployed `--no-verify-jwt` and gated by an `x-cron-secret` header (function secret `CRON_SECRET`, same value in Vault as `avisos_cron_secret`). `?modo=diario` (meant for 19:00 AR): ONE push per family listing tomorrow's eventos (festejos only to who sees them, minus `asiste="no"`) + colectas due the day after tomorrow to families with an unpaid hijo in that curso. `?modo=semanal` (Sunday 18:00 AR): per-family "Esta semana: N eventos · N colectas por pagar · N cumples", skipped when empty. Dedupe via `avisos_automaticos_log` (unique `clave`, inserted before sending; `supabase/avisos-automaticos.sql`). Also in diario: autorizaciones whose `fecha_limite` is tomorrow → "✍️ Falta tu respuesta" to families with an unanswered hijo in that curso. Families can turn each type off in `preferencias_avisos` (`supabase/preferencias-avisos.sql`; no row = all on; UI: web `PreferenciasAvisosModal` from the account menu "🔔 Notificaciones", mobile Más → Notificaciones switches; list of types in `src/lib/avisos.js` / `@shared/avisos`) — only automatic avisos, live pushes always arrive. Sending (Expo API, ticket + background receipt pruning of dead tokens) lives in `supabase/functions/_shared/expoPush.ts` (`enviarPush(sb, [{usuario,title,body,data}])`), shared by `send-push` and `avisos-automaticos` — redeploy both after touching it. `&dry=1` computes without logging/sending and returns a text sample; with dry, `&hoy=AAAA-MM-DD` simulates another day — use that to test, never a real run. Scheduling (pg_cron + pg_net + Vault) lives in `supabase/avisos-automaticos-cron.sql`. New push `type: "resumen"` → Muro in both TAB_MAPs.
- **Calendar sync (ICS feed)** — Edge Function `supabase/functions/calendar-feed/index.ts`, the one exception to "every Edge Function expects a JWT": it's deployed with `supabase functions deploy calendar-feed --no-verify-jwt` because Google/Apple/Outlook poll it directly with no Supabase session — the `?token=` query param *is* the auth, checked server-side with the service-role key against the **`usuario_calendar_tokens`** table (`usuario_id` PK, `token` unique — moved out of `usuarios.calendar_token` 2026-08-25: that column was readable by any curso-mate via the `usuarios_select` RLS policy, a real cross-curso ICS-feed leak; `usuario_calendar_tokens` has its own RLS restricted to `usuario_id = mi_usuario_id()`, never by shared curso). The token is generated/regenerated via the RPC `regenerar_calendar_token()` (`supabase/calendar-sync.sql` + `supabase/calendar-token-hardening.sql`, `security definer`, same pattern as `crear_apoderado`/`verificar_codigo`). The feed combines `eventos`, cumpleaños (hijos + maestros), and recordatorios that carry `hora_inicio` (the "citas" with a real schedule — a recordatorio without `hora_inicio` is just a text/aviso and stays out of the calendar); festejos are `eventos` with `tipo="festejo"` and are **visible only to who they concern** (2026-09-23, `supabase/festejos-solo-invitados.sql`): RLS `eventos_select` lets a festejo through only to families with an invited hijo (or invited directly via `evento_asistencia.usuario_id`), the cumpleañero's family (`es_padre_de(alumno_id)`), its creator, and super/colegio_admin — a Room Parent sees it only if one of those applies; every other evento type is still visible to the whole curso. The feed reads with the service role, so it applies the same rule by hand (`leToca`). **Every fetch is logged** on the user's `usuario_calendar_tokens` row (`supabase/calendar-feed-lecturas.sql`, 2026-09-23): `leido_en`/`leido_por` (User-Agent) for any client, plus `google_leido_en` when the UA matches `Google-Calendar-Importer` — the only real proof a Google subscription is working ("Ya lo agregué" just records that the user *thinks* they finished). Both calendar buttons read `google_leido_en` to show "✓ Google Calendar ya está leyendo tu calendario (última vez hace X)" and count as synced; `regenerar_calendar_token()` clears the three columns. Android Google Calendar app gotcha: a URL-subscribed calendar arrives with "Sincronizar" **off** (listed in the app's Settings, missing from the drawer) — the guided steps now include turning it on. The VCALENDAR carries `X-WR-CALNAME:Tribbu` so it doesn't show up in Google/Apple/Outlook under the raw function URL (note: some clients, notably Google Calendar, only read `X-WR-CALNAME` at subscribe time — a calendar added before this existed needs to be removed and re-added to pick up the name). **Google Calendar's polling of a subscribed-by-URL calendar is infrequent and outside our control** (observed: an event's `hora_inicio` edited in the app took well over an hour to show correctly in Google Calendar, still showing the old time in between) — if a user reports "I changed the time/date in the app but Google Calendar still shows the old one," that's expected Google-side caching, not a feed bug; removing and re-adding the subscription sometimes (not reliably) forces an immediate re-fetch. Google Calendar's "Add by URL" (`calendar.google.com/calendar/render?cid=`) specifically requires the `cid` value to use the `webcal://` scheme, not `https://` — the web sync button converts it before opening that link (mobile's iOS `webcal://` open already did). UI: `src/features/calendario/BotonAgregarCalendarioWeb.jsx` (web) and `mobile/features/calendario/BotonAgregarCalendario.jsx` (mobile), both wired into their respective `calendario/index.jsx`. The mobile flows are per-platform (`specs/eleccion-de-calendario-mobile.md`): **iOS** picks Apple Calendar (`webcal://` open) or Google Calendar (`render?cid=` opened via `expo-web-browser`'s SFSafariViewController — universal links don't fire inside it, so the native Google Calendar app can't intercept); **Android** has no working web shortcut at all (`calendar.google.com` is an App Link of the Google Calendar app, which fakes success on `?cid=`; Google also blocks login in embedded WebViews), so mobile shows the **same two-option chooser on both platforms** — "Calendario del dispositivo" vs "Google Calendar" — and each option uses whatever mechanism actually works on that OS (table in the component header). **iOS/dispositivo** = `webcal://` (Apple Calendar subscribes to a native "Tribbu" calendar the server pushes to; strictly better than writing events ourselves, no calendar permission). **Google (both platforms, identical)** = the **guided subscription** described below — iOS used to open `render?cid=` in an SFSafariViewController, dropped 2026-08-28 so the experience matches Android (users who already did it keep `metodo="gcal"`, still counted as synced). **Android/dispositivo** = `expo-calendar` (native module — regenerate `mobile/android/` after (un)installing it) with the engine in `mobile/lib/calendarSync.js`: fetches the same ICS feed, minimal parser for our own generator's format, creates a device-local **"Tribbu" calendar**, UID→deviceEventId map in AsyncStorage, delete-and-recreate on change, removal of events gone from the feed, re-sync on Calendario mount/app foreground throttled to 1/hour, and "Desconectar" deletes the whole calendar. Known and deliberately accepted (2026-08-28): that calendar is `account_type=LOCAL` — visible in Samsung/AOSP calendar apps with its own color/toggle, but **the Google Calendar app does not list or draw third-party LOCAL calendars** (verified in the emulator against a real account: `visible=1`, 108 events, still absent from drawer and grid) and it never reaches calendar.google.com; the option's copy says so and points Google Calendar users to the other option. **Google** = **guided subscription**: the app hands over the feed link ("Copiar enlace" / "Enviármelo por mail" via `mailto:`) plus the 4 steps to add it **once** from `calendar.google.com` on a computer ("Otros calendarios" → + → "Desde URL"), and a "Ya lo agregué" button that persists `metodo="suscripcion"`. That is the only path that yields a real **"Tribbu" calendar inside the Google account** (`ownerAccount …@import.calendar.google.com`, own name/color/toggle, syncs everywhere — verified); creating one from the app would need the Calendar API + OAuth, out of scope, and the phone-side shortcuts all fail (`calendar.google.com` is an App Link the Google Calendar app hijacks with a fake success; embedded WebView login is blocked). `metodo` in AsyncStorage (`calsync_<userId>`) records what the user actually did: `webcal`/`device`/`suscripcion` (+ legacy `gcal`) = synced, `copia` = only copied the link; legacy `google`/`1` are treated as `copia`. **Crash fixed 2026-08-28 in `calendarSync.js`**: cumpleaños (the only all-day + `RRULE:FREQ=YEARLY` VEVENTs) are expanded in the parser to one plain event per year (`ANOS_RECURRENCIA = 3`, UID `<uid>::<año>`) instead of passing `recurrenceRule` — for an all-day recurring event expo-calendar emits `DURATION="PT86400S"`, `CalendarProvider2.fixAllDayTime()` parses it with a naive substring (`Integer.parseInt("T86400")`) → `NumberFormatException` that escapes `saveEventAsync`'s narrow catch and **kills the process**, invisible to any JS try/catch. Timed events may still carry `recurrenceRule`. See `specs/sincronizacion-de-calendario.md` + `specs/eleccion-de-calendario-mobile.md`.

### Core data model (Supabase tables)
`usuarios`, `usuario_calendar_tokens` (`usuario_id`/`token`, own table + RLS for the ICS feed token — see calendar-feed above), `cursos` (`año_lectivo integer not null` since 2026-08-25 — each school year's "1ºA - Primaria" is a separate row; see "Año lectivo / promoción de curso" below), `hijos`, `usuario_hijos` (parent↔child), `usuario_cursos` (user↔course with `rol`), `cumples`, `eventos` (+`evento_asistencia`, which cascades on delete since 2026-09-24; `fecha_fin` for multi-day events; **edit/delete** = `puede_editar_evento()` in `supabase/eventos-permisos-edicion.sql`: `super` any evento on the platform; `colegio_admin` only eventos **created by the colegio** (creator is a colegio_admin of that colegio or a super — `evento_creado_por_colegio()`); everyone else, **Room Parent included**, only what they created; for a festejo also the cumpleañero's other parent (Yanina's rule, 2026-09-24). `eventos.alumno_id` cascades on delete so dropping an alumno still removes their family-created festejos. The family calendar shows ✏️/🗑 only for `creado_por === userId` (web+mobile, also in Todos) and excludes the virtual recordatorio "comunicados" by id prefix `r-`, not by `tipo` (real eventos can have `tipo="comunicado"`); editing never overwrites `creado_por`. The colegio manages them from Super Admin → Comunidad → "📅 Eventos" (`EventosColegio` in `src/features/calendario`, and its RN port in `mobile/features/calendario` as the mobile panel's "📅 Eventos" module): every evento of the year's cursos with its creator, filters curso/tipo/próximos-pasados/search, ✏️/🗑 only where the RLS allows, festejos delete-only; "+ Nuevo evento" pushes to the curso like any new evento), `recordatorios` (+`recordatorio_leidos`, `grupo_id` for multi-curso Comunicaciones — surfaced to users as a "🏫 Comunicación del colegio" badge + an origin filter in Recordatorios/Muro/Notificaciones (web+mobile), since it's otherwise indistinguishable from a Room Parent's own recordatorio, `hora_inicio`/`hora_fin` optional `time` columns, `titulo text` nullable (2026-09-22) — `titulo`/`hora_inicio`/`hora_fin` can be set both from the Comunicaciones form (`ComunicacionesAdmin`, web + mobile Super Admin) and, since 2026-09-23, from the regular Recordatorios create/edit form (any apoderado/Room Parent, web + mobile): título optional, horas only when there is a fecha and fin only with inicio (mobile types "18:00" and normalizes it via `normalizarHora`). A recordatorio without `titulo` renders exactly as before. When `titulo` is set, `texto` is its description body (same `titulo`/`descripcion` split as `eventos`) — everywhere a recordatorio is rendered (Recordatorios, Muro, Notificaciones, `calendario`'s "comunicado" virtual events, web+mobile) shows `titulo` as a bold heading above `texto` when present, falling back to `texto` alone exactly as before when it's `null`; `fmtRangoHora()` in `src/lib/helpers.js` formats the hora range and is used in Recordatorios/Muro rows too; a recordatorio with `hora_inicio` set is also synced as a timed VEVENT by `calendar-feed` (SUMMARY = `titulo||texto`, plus a DESCRIPTION line with `texto` when `titulo` is set) — see below), `colectas` (+`colecta_pagos`; `creado_por` since 2026-09-24, defaulted server-side to `mi_usuario_id()`; **edit/close/delete** = `puede_gestionar_colecta()` in `supabase/colectas-permisos.sql`: super, the colegio, the curso Room Parent, the `responsable_id` and the creator — before, any curso member could. The web/mobile Finanzas card shows Cerrar/Reabrir on the same rule (`gestionaColecta` in `src/lib/muro.js`), editing no longer re-opens a closed colecta, and a colecta open 15+ days past its límite (`colectasPorCerrar`, `DIAS_PARA_CERRAR`) shows a "⏰ Venció hace N días… Cerrar colecta" banner on its card and a 🔒 "¿Terminó la colecta?" item in Muro Pendientes for whoever manages it — never auto-closed, late payers are real), `menu`, `alertas`, `contactos`, plus útiles/libros/uniformes tables. Festejo RSVP (`evento_asistencia`): besides `hermanos`/`adultos`/`comentario`, the optional age of each sibling in `hermanos_edades smallint[]` (one slot per hermano, `null` = not given; `supabase/festejos-edades-hermanos.sql`, 2026-09-23) — helpers `ajustarEdades`/`edadesParaGuardar`/`fmtEdadesHermanos` in `src/lib/festejos.js` (`@shared/festejos`), shown in the organizer list ("2 herm. (3 y 6 años)") and exported as an "Edades hermanos" Excel column, web + mobile. `encuestas` (+`encuesta_opciones`, `encuesta_votos` — per-curso polls, any role can create, one vote per apoderado via `unique(encuesta_id, usuario_id)`, `encuesta_votos.opcion_id` is FK'd compositely against `encuesta_opciones(id, encuesta_id)` so a vote can't reference an option from a different poll; see `specs/encuestas.md`). `push_tokens` (Expo push tokens per device, used by the mobile app). `recordatorios.adjuntos` and `eventos.adjuntos` are `jsonb DEFAULT '[]'` arrays of `{url, tipo, nombre}` pointing at the (now private) `adjuntos` Storage bucket — `url` is the storage path, signed on render (see "Storage buckets" above and `specs/adjuntos-en-recordatorios-y-eventos.md`). `colegio` is the **old** singleton school-info row (`id="d31b5547-246b-46fa-906e-950e51d4af58"`), superseded 2026-09 by `colegios` (plural, real multi-tenant table — see "Multi-colegio" below) but left in the DB unused rather than dropped. `backup_tribbu.cjs` no longer keeps a table list: it discovers every `public` table from PostgREST's OpenAPI schema, so new tables are backed up automatically.

**Año lectivo / promoción de curso** — spec `specs/ano-lectivo-y-promocion-de-curso.md`, Super Admin web only (no mobile UI). `cursos.año_lectivo` makes the course itself year-scoped instead of adding a year column to every content table: promoting a student is just `hijos.curso_id` pointing at the new year's curso row, so recordatorios/eventos/colectas/alertas/encuestas/menu/horarios tied to the old curso row stay correctly isolated with **zero query changes** anywhere in the app — `curso_id` keeps meaning exactly what it means today, and "Mi acceso" needs no explicit year filter since `items` is derived from `hijos.curso_id`. In `src/features/superadmin/index.jsx`: the "Cursos" screen has its own year selector (any year, for auditing/promotion setup) and a "Duplicar para el año siguiente" action per curso (`clonarConfiguracionCurso`) that clones horarios/`usuario_cursos` (Room Parent)/`maestro_cursos`/`uniforme_cursos`/`utiles`/`libros` to a new curso row at `año_lectivo+1` — students are never copied by this action. Every other curso selector in Super Admin (the shared `CursoListSelector`, plus the Alumnos/Maestros pickers) filters to `año_lectivo === año vigente` (`colegio.año_lectivo_actual`) by default, computed once in `SuperAdmin()` as `cursosAnoActual`. A new "🎓 Promoción" section (`PromocionCurso`) does the actual bulk move: pick a curso origen (año vigente) + curso destino (año vigente+1, must already exist via "Duplicar"), see all its alumnos pre-checked, uncheck repeaters/leavers, confirm — one `hijos.curso_id` bulk update for the checked ids. Non-promoted students are left untouched (old `curso_id`, no `activo`/egresado flag in v1).

**Multi-colegio (multi-tenant)** — spec `specs/multi-colegio.md`, web only so far. `colegios` (plural) replaces the old singleton `colegio`: `nombre`/`logo_url`/`color_primario`/contact fields/`año_lectivo_actual` **per colegio**. `cursos.colegio_id`, `menu.colegio_id`, `contactos.colegio_id`, `uniformes.colegio_id` (all `not null`) anchor the tenant boundary; everything else that hangs off `curso_id` (hijos, maestros via `maestro_cursos`, eventos, recordatorios, colectas, cumples, alertas, horarios, útiles, libros, `uniforme_cursos`, encuestas, códigos de invitación) is scoped **transitively** through `curso_id → cursos.colegio_id`, with zero new columns on those tables — same "parent row carries the scope" trick as año lectivo, one level up. `menu.fecha` stopped being globally unique; it's now `unique(colegio_id, fecha)` (`onConflict:"colegio_id,fecha"` in every menu upsert, web and mobile). Two roles: `super` (unrestricted, unchanged — now conceptually "platform operator", the only one who can create a new colegio) and new **`colegio_admin`** (`usuarios.colegio_id`, same functional reach as today's Super Admin panel but hard-scoped to that one colegio via RLS). `admin` (Room Parent, per-curso) and `padre` are untouched — no naming collision. RLS: `supabase/multi-colegio.sql` adds an `es_colegio_admin_de(colegio_de_X(...))` alternative next to every existing `es_super()` check across `rls-hardening.sql`'s tables plus `encuestas.sql`'s (new helpers `colegio_de_curso`/`_hijo`/`_evento`/`_colecta`/`_recordatorio`/`_util`/`_libro`/`_uniforme`/`_uniforme_item`/`_encuesta`, `es_colegio_admin_de_maestro`, `es_colegio_admin_de_usuario`) — additive everywhere except `menu`/`uniformes`/`uniforme_items`/`contactos` SELECT, which go from "any authenticated" to "member of that colegio" (harmless for every real user today, who's always a member of some curso). `src/features/superadmin/index.jsx` serves **both** roles from one component: `colegio_admin` gets exactly today's panel, pre-scoped by RLS with no query changes; `super` gets an extra "Plataforma → 🌐 Colegios" section (list + "+ Nuevo colegio", which creates the `colegios` row and, optionally, its first `colegio_admin` via `manage-auth-user`) and, on entering a colegio, a client-side `colegio_id` filter layered over the same queries (RLS alone doesn't scope `super`, by design). Beyond that first admin at colegio-creation time, `super` manages a colegio's `colegio_admin` accounts ongoing from the regular "👤 Usuarios" screen (once entered into that colegio): the create/edit-user modal gets a second "Acceso especial" toggle, "◇ Admin de Colegio" — next to the existing "◇ Super Admin" one, shown only to `super` (never to `colegio_admin`, matching the RLS privilege-escalation guard) and only while a colegio is entered (`colegioId` set) — which sets `rol:"colegio_admin"` and `colegio_id` to that entered colegio on save; a `colegio_admin` also shows up tagged with an "Admin de Colegio" pill/filter chip in that same list (`ROL_LABEL`/`ROL_COLOR`/`ROL_BG` in `src/lib/theme.js` gained a `colegio_admin` entry, amber, alongside `padre`/`admin`/`super`). Note the Rol filter is duplicated between `ctrlUsuarios`'s `useListControls` config (drives matching) and a second inline array passed straight to `<ListToolbar>` (drives the rendered chips, with `color`) — pre-existing duplication in this file, not introduced by multi-colegio; keep both in sync when touching rol options. `src/features/contacto/index.jsx`'s `Contacto` component takes a `colegioId` prop now instead of the hardcoded singleton id (falls back to "the only colegio row" when not given — today there's just one, so every caller that hasn't been threaded through yet still works). **Branding** (2026-09-23): `logo_url` shows next to the wordmark (web sidebar/header, mobile `AppHeader`); `color_primario` (validated `#RRGGBB` via `colorColegio()` in `src/lib/helpers.js` — web picks it with `<input type=color>` in Contacto, mobile `ColegioAdmin` with an 8-swatch palette) colors the wordmark dot and replaces the default blue accent (`hijoDotColor` fallback) but **never** a hijo color the user picked; the desktop sidebar subtitle shows the colegio name instead of "Comunidad escolar". None of it applies in Todos (`colegioActivo` is null there). **Known gaps, deliberately deferred**: parent-facing mobile screens still resolve menu writes to "the only colegio" when no `colegioId` is passed; "Mi acceso"/`tagDeCurso` hasn't been extended to tag items by colegio for a parent with kids in >1 colegio (moot today — only one colegio exists).

## Mobile app — `mobile/` (Expo · iOS + Android)

A separate **React Native (Expo, managed)** app living in `mobile/`. It does **not** touch the web app (`src/`) beyond the env/storage-injection refactor described above. See `mobile/README.md` for setup/EAS/backend steps.

- **Shared logic, not copied**: Metro `watchFolders` + a Babel `@shared` alias point at `../src/lib`, so `theme.js` and the pure helpers feed both web and mobile from one source. Env and storage are injected per platform (`mobile/lib/config.js` → `EXPO_PUBLIC_*` + AsyncStorage). The Supabase client (`mobile/lib/supabase.js`) uses AsyncStorage + `AppState` auto-refresh; the session persists across restarts. `mobile/lib/push.js` / `authAdmin.js` are thin client-coupled wrappers of the same Edge Functions.
- **Navigation = Expo Router**: `mobile/app/` — root `_layout.jsx` is the auth gate (login / `(tabs)` / `(super)`). The web's three layouts collapse into one mobile layout; Super Admin gets its own stack. `(tabs)/_layout.jsx` renders the persistent `AppHeader` (A3 pattern: notifications bell with unread dot + active-child chip that opens the color picker; the multi-child/course selector row appears below when there's more than one access — account actions live in "Más": Cambiar contraseña + Cerrar sesión) above the custom `FloatingTabBar`. The most relevant skill here given the React + Vite codebase — consult it before adding components or effects.

- **web-design-guidelines** — reviews UI code against Web Interface Guidelines. Use when asked to **review UI/UX, audit design, or check accessibility**.
- **agent-browser** — browser-automation CLI for AI agents. Use when a task needs to **drive a real browser**: navigate pages, fill forms, click, screenshot, scrape, or QA/test the running web app. Prefer it over built-in browser/web tools.
- **spec** — generates a feature spec grounded in tribbu's architecture. Use when the user wants to **plan or specify a new feature before implementing it**. Reads `specs/_template.md` + this file, asks clarifying questions, then writes the spec to `specs/<name>.md`.
- **implement** — full plan → implement → validate → document workflow for a **new feature** end-to-end. Use when the user wants to **build a feature** (not just spec it): asks clarifying questions, implements following tribbu conventions, validates with lint + build + manual QA, and updates `CLAUDE.md`/the spec. - **fix-bug** — investigate → root-cause → minimal fix → self-validate workflow. Use when the user **reports a bug or regression to fix**. Traces the real code path (App shell / feature / lib / Supabase), presents the root cause before changing code, and **must self-validate the fix** (lint + build + manual QA in the running app via agent-browser) before claiming it works — tribbu has no test suite.

## Repository hygiene

The root `*.cjs` scripts (`hash_passwords`, `migrate_to_auth`, `migrate_remaining`, `reset_passwords`, `backup_tribbu`) are **one-time** Node migration/backup utilities that connect to the live project with the service-role key, read from `SUPABASE_SERVICE_ROLE_KEY` in the environment (never hardcoded — run as `SUPABASE_SERVICE_ROLE_KEY=... node <file>.cjs`, a real key was found hardcoded in all five on 2026-08-25 — **it was NOT actually rotated**: verified 2026-09-23 that the legacy `service_role` JWT from those old commits still works, and the GitHub repo is **public**, so it must be invalidated in the Supabase dashboard (see PENDIENTES.md → Urgente)). Do not run them casually, and do not put a real key back in the file or copy that pattern into `src/`. **`backup_tribbu.cjs` is the exception — it's the ongoing, read-only full backup** (rewritten 2026-09-23): writes `tribbu_backup_<fecha>/` (gitignored) with `data.json` (every `public` table, discovered via PostgREST's OpenAPI and paginated by PK — before, it had a hand-kept list missing newer tables and silently truncated any table over PostgREST's 1000-row cap), `auth_users.json` (id/email/dates — Auth never exposes password hashes) and `storage/<bucket>/…` (every file in `adjuntos`/`eventos`/`libros`; `--sin-archivos` skips it). The service key can be fed without pasting it via the logged-in Supabase CLI: `npx supabase projects api-keys --project-ref gctymjhblvocvaenmdhr -o json`.
