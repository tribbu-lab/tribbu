## What this is

**tribbu** is a school-community ("comunidad escolar") mobile/web app: parents (apoderados), Room Parents (admins) and a Super Admin coordinate per-classroom (`curso`) life — calendar, lunch menu, birthdays, reminders, fundraisers (colectas), contacts, etc. React + Vite SPA, Supabase backend, packaged as an Android app via Capacitor + OneSignal push. The domain and all UI copy are in Spanish — match that when writing new strings.

## Commands

```bash
npm run dev       # Vite dev server (web)
npm run build     # production build to dist/
npm run preview   # serve the built dist/
npm run lint      # ESLint (flat config in eslint.config.js)
```

There is **no test suite** and no test runner configured. `npm run lint` is the only automated check. Web lint is at **0 errors** (2026-09-23) and CI (`.github/workflows/ci.yml`: web build + lint, mobile lint + Metro bundle) blocks on errors; the ~45 remaining **warnings** are the app-wide `useEffect(()=>{ cargar() },[...])` data-loading pattern (`react-hooks/set-state-in-effect` downgraded to warn + `exhaustive-deps`) — converting those loaders to `useCallback` is a separate refactor. Keep new code error-free.

Android (Capacitor wraps the built `dist/`):
```bash
npm run build && npx cap sync android   # rebuild web + copy into android/
npx cap open android                    # open in Android Studio
```

## Environment

Copy `.env.example` to `.env`. Required: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`. Also referenced in code: `VITE_ONESIGNAL_APP_ID` (push). The client only ever uses the **anon** key; the service-role key must never appear in `src/`.

## Architecture

### App shell — `src/App.jsx`
**Code-splitting (2026-09-25):** every feature tab (and `SuperAdmin`, `BusquedaGlobal`) is `React.lazy`-loaded through the `aLazy()` helper at the top of `App.jsx`, with `<Suspense fallback={<Spinner/>}>` around `renderTab()` and the Super Admin screen — the initial bundle went from ~1.35 MB to ~470 KB. `xlsx` is never imported statically: the four places that use it do `const XLSX = await import("xlsx")` inside the export/import handler. Keep new features lazy and new heavy libs dynamic. **Tab cache (2026-10-01)**: `renderTabs()` keeps every visited tab mounted and hides the inactive ones with `display:none` (each in its own `Suspense`), so going back to a tab is instant instead of a full remount + reload; changing hijo/curso (`ctx` = usuario|cursoIdx|cursoIds) drops all but the current one; Marketplace/Servicios/Comunidad share one cache slot. Each tab gets `TabActivaContext` (`src/hooks/useTabActiva.js`): `useCargar` (and the Muro's own effect) skip loading while hidden and re-run `cargar` in the background when the tab becomes visible again — so a screen's `cargar` must **not** blank its content (no `setCargando(true)`/`setDatos(null)` that swaps the list for a spinner) or the instant return is lost. New tab screens should load through `useCargar`. The desktop global search covers the tabs instead of unmounting them.
A single ~520-line component that owns nearly all top-level state and routing. There is no router library; `tab` state drives a `switch` in `renderTab()` that mounts one feature. Since 2026-09-23 `tab` is mirrored in the URL as `?tab=<id>` (no param = `muro`) via `history.pushState` + a `popstate` listener, so browser back/forward move between tabs and a section link survives login (`tabDeUrl()`/`TABS_VALIDOS` in `App.jsx`). Query, not hash — the hash belongs to the password-recovery link. `?tab=admin` without `isAdmin` renders the Muro. Super Admin's own sections are not URL-synced. Key responsibilities:
- **Session bootstrap**: on mount, `supabase.auth.getSession()` → load the `usuarios` row (joined with `usuario_hijos` + `usuario_cursos`) by `auth_id`, shape it into the `usuario` object.
- **"Mi acceso" model**: `items` = the user's children (`hijos`) plus any courses where they are a Room Parent. `cursoIdx` selects the active item; `rolEfectivo` ("padre" | "admin") is derived per-item — **a user can be a parent in one course and admin in another**. With hijos in more than one curso, a pseudo-item **"Todos"** is prepended (first and the login default): the **global unified view**, mirroring mobile. The contract every feature follows (all passed as props from `App.jsx`): read with `.in("curso_id", cursoIds)` (`cursoIds` = all cursos with hijos in Todos, `[cursoId]` per-hijo, memoized for stable identity); `esVistaTodos` bool; `cursoId` **null** in Todos; `isAdmin` false in Todos; `tagDeCurso(curso_id)` → `{nombre, color}` only in Todos, used to tag rows (8px identity-color dot + first name); writes use the entity's `curso_id`, never the session `cursoId`. Single-curso users see zero change. Spec: `specs/vista-unificada-hijos-mobile.md`.
- **Three layouts** rendered from the same state: Super Admin (`usuario.rol==="super"` → only `<SuperAdmin/>`), mobile (bottom tab bar + "Más" menu), and desktop (fixed sidebar). When changing navigation/header, update all three.
- **Super Admin's own navigation** (`src/features/superadmin/index.jsx`) — **rediseño sobrio (2026-10-22)**, same criterio as the apoderado's 4 sections: the ~25 screens (each still its own `sec`) are grouped into **6 sections** in `SECCIONES` (`{id:"g_…", l, icono, items}`): **Inicio · Comunicación** (Comunicados/Alertas/Eventos/Autorizaciones) **· Mensajes** (De familias/Del personal — `soloColegioAdmin`, so `super` doesn't get this section) **· Comunidad** (Talleres/Marketplace/Lost & Found/Denuncias/Adopción) **· Personas** (Apoderados/Alumnos/Maestros/Directivos) **· Colegio** (Cursos/Materias/Horarios/Uniformes/Menú/Datos y membrete/Promoción — última porque se usa una vez por año), plus `SECCION_PLATAFORMA` (Colegios/Soporte/Super Admins) first for `super`. Line icons from `Icono` (new `escuela`/`corazon`/`globo`), no emojis in nav or titles. Desktop: dark `#0F172A` sidebar with the 6 sections, and at the bottom **Ayuda y soporte** (`soporte_colegio`, staff only) + **Mi cuenta** (`sec=="cuenta"`: name, rol · colegio, Cambiar contraseña, Ayuda, Cerrar sesión). The content header is the section title + `SubSeccion desplazable` (new prop: scrollable row that keeps the active tab in view) + the screen's `SECCION_INFO` description and its `BotonNuevo`. Phone width (<768px): top bar with wordmark, rol · colegio and the initials (→ Mi cuenta), then one "<icono> <sección> ⌄" button that unfolds the section list (`navAbierta`); the big title is hidden there (the button already says it). `seccionesVisibles` drops empty sections: the Secretaría (`SOLO_ADMIN_COLEGIO`) keeps Comunicación, Mensajes, Comunidad (Talleres/Adopción), Personas (Apoderados/Alumnos) and Horarios — a section left with a single screen takes that screen's name and icon (`ICONO_PANTALLA`), so the Secretaría sees "Horarios" instead of a confusing "Colegio" (web + mobile). Row actions use `Icono` lápiz/papelera; empty lists use `EmptyState`. **Unread badges** (red, like the apoderado sidebar) on the Mensajes section, its De familias / Del personal tabs and Ayuda y soporte: `useNoLeidosPanel(activo, sec)` (web `src/hooks`, mobile `mobile/lib`; `bandeja_colegio` + `mis_conversaciones` → `noLeidosPanel` in `@shared/mensajes`), refreshed on each Realtime message, on resync, every 60 s and when `sec` changes (reading a chat fires no `mensajes` event). **Inicio** (`InicioColegio`, `src/features/superadmin/inicio.jsx`) looks like the apoderado's "Hoy": fecha + "Hola, Ana" + colegio, "Tenés N cosas para resolver" (first one highlighted, the rest in one card, each with an "… →" link to its `sec`: family messages via `bandeja_colegio`, **unread staff messages + soporte replies via `mis_conversaciones`** (tipo `personal`/`soporte`), pending denuncias, talleres awaiting approval, weekdays without menú, alumnos without apoderado, cursos without horario; filtered by `ocultas` for the Secretaría) or "Estás al día", "El colegio en números" (one card), Próximos días (date column, no chips, multi-curso deduped by `grupo_id`) + open autorizaciones as a link, Accesos rápidos as icon rows; one parallel request batch. Mobile app (`mobile/features/superadmin/index.jsx`) mirrors the same sections (MaterialCommunityIcons `-outline`; no Promoción/Marketplace/Lost & Found there, they're web-only): home = fecha + "Hola" + rol · colegio, the super's COLEGIO selector, numbers card, a list of sections (`Fila`) and Ayuda y soporte / Mi cuenta (with `CambiarPasswordModal` + logout); a section shows "‹ Panel", its title and `PestanasPanel` (`mobile/components/SubTabs.jsx`, scrollable, no routes); "+ Agregar…" buttons are `BotonNuevo`. **Push in the panel** (2026-10-22): `useNotificationRouting(true, { panel: true })` runs in `app/(super)/index.jsx` (before, only `(tabs)` had it, so a tap did nothing useful) and `router.navigate`s to `/(super)?sec=…&c=…&t=…` (`PANEL_SEC`: soporte, denuncia, autorizacion, taller, evento, recordatorio, alerta); for a `mensaje` the panel reads `conversaciones.tipo` of `c` → `mensajes_personal` (and opens that chat via `<Mensajes soloPersonal abrirConv nonce>`), `mensajes_familias` (colegio/docente) or `soporte_colegio`/`soporte`. Promoción stays web-only; the mobile **Colegio** module is contact-info-only (`ColegioAdmin` — edits the `colegios` row: nombre/teléfono/email/dirección/horarios/sitio/mapa + `logo_url` via `pickAndUploadImage`), without the year-scoping/duplication tools of the web "Cursos" screen. This mobile panel now serves **both** `super` (`isSuper`) and **`colegio_admin`** (`esColegioAdmin` from `useSession()`); routing to it is `isSuper || esColegioAdmin` in `mobile/app/_layout.jsx` (`vaAlPanel`), and the panel branches on `esColegioAdmin` to hide the "◇ Super Admin" toggle in the apoderado create/edit modal (`ocultarAccesoEspecial`). `colegio_admin` scoping is pure RLS (`supabase/multi-colegio.sql`), no client-side `colegio_id` filter — same as the web. See `specs/colegio-admin-en-mobile.md`. **`super` on mobile** (2026-09-23) gets a "COLEGIO" selector at the top of the panel (defaults to the first colegio by `creado_en`) and `cargar()` applies the same client-side `colegio_id` filter as the web (RLS doesn't scope `super`) — before, it mixed every colegio's data and couldn't create cursos. `activeColegioId` (= `miColegioId` for `colegio_admin`) feeds curso creation, `ColegioAdmin`, `UniformesAdmin` (which also stopped failing silently on new categorías: it inserted without the NOT NULL `colegio_id`) and `Comedor`/`UploadMenuExcel` via a new `colegioId` prop. No "Plataforma" section on mobile (creating colegios stays web-only).
- **Push deep-linking**: OneSignal notification clicks dispatch a `tribbu:navigate` CustomEvent; `TAB_MAP` maps notification `type` → tab id. `window._tribbuPendingTab` / `_tribbuUserId` bridge the native plugin and React.

### Storage buckets (`supabase/storage-privado.sql`, 2026-09)
`adjuntos` (recordatorio/evento attachments + colegio logos at `colegios/{id}/logo.*`) and `eventos` (festejo invitation images) are **private**: no `getPublicUrl`, every access is signed on render (1 h TTL). `libros` (textbook cover images) stays **public** on purpose. `src/lib/storageUrl.js` (+ `mobile/lib/storageUrl.js`) = `parseStoragePath` / `signStorageUrl`; `src/components/SignedImg.jsx` (`<SignedImg src bucket>` + `useSignedUrl` hook) / `mobile/components/SignedImage.jsx` (`<SignedImage>`) render private images. `parseStoragePath` accepts **both** a bare path (new rows) and an old full `/object/public/<bucket>/…` URL (pre-migration rows) — new uploads store the bare path. `mobile/lib/media.js`'s `pickAndUpload*` return the path for private buckets, the public URL for `libros`. Storage RLS: SELECT for `authenticated` on the private buckets (was: anyone on the internet). **Two old `public`-role read policies ("Allow public read" on eventos, "adjuntos_read") had survived that migration** — found 2026-09-23 (anon key could list/download both buckets) and dropped in `supabase/storage-cerrar-publico.sql`, which also limits "upload libros" to `authenticated`. When touching Storage policies, check `pg_policies.roles`, not just the `qual`. When adding a new place that shows one of these images, use `<SignedImg>`/`<SignedImage>`, never `getPublicUrl`. **Miniaturas (2026-10-01)**: the plan has no Storage image transformations, so every image upload also stores a small `<path-sin-ext>.thumb.jpg` (≤320 px, `pathMiniatura` in `src/lib/miniaturas.js`, `@shared/miniaturas`) next to the original, and the original itself is re-encoded to JPEG ≤1600 px (web: `subirImagen`/`prepararImagen` in `src/lib/imagenesWeb.js`, canvas; mobile: `pickAndUploadImage` in `mobile/lib/media.js` via the native `expo-image-manipulator`; skipped for colegio logos — `conMiniatura:false` —, the public `libros` bucket, GIF/SVG and PDFs). Anywhere an image is shown small, pass `miniatura` to `<SignedImg>`/`<SignedImage>` (`signStorageUrl(..., { miniatura: true })`): it signs the `.thumb.jpg` and falls back to the original on 404 (the 404 is cached, so it isn't retried every render); full-size views (lightbox, detail) keep the original. `borrarArchivos` also removes the `.thumb.jpg`. Images uploaded before this have no thumbnail until `miniaturas_backfill.cjs` (root, service key via env, `--dry` first; pure-JS `jimp` because Windows Application Control blocks sharp's native binary here) generates them — it only adds `.thumb.jpg` files, never touches originals.

### Backend & auth
- Auth is **Supabase Auth** (`signInWithPassword`, `resetPasswordForEmail`). The `usuarios` table row is linked by `auth_id`. `bcryptjs` is no longer imported by the app (removed 2026-09-23); the dependency stays only for the one-time root `*.cjs` migration scripts.
- **Self-registration via invitation code — removed 2026-09-11**: apoderados used to be able to sign themselves up with a per-curso code shared by their Room Parent ("Registrarme con código de invitación" on Login, both web and mobile — `RegistroConCodigo` in `features/auth`) or have Super Admin manage those codes ("🔑 Códigos" module, `CodigosInvitacion` in `features/superadmin`, both platforms). All of that UI is gone; apoderado accounts are now created only from Super Admin ("👤 Usuarios" → nuevo apoderado). **Not** touched, on purpose: the RPCs `verificar_codigo`/`crear_apoderado` and the `codigos_invitacion` table (`supabase/rls-hardening.sql`) — nothing in the client calls them anymore, but the table/RLS/functions are left in place rather than dropped. `eliminarCurso`'s cleanup (deletes `codigos_invitacion` rows for a curso being removed, alongside `horarios`/`usuario_cursos`/etc.) is unrelated and was kept.
- **Password recovery** (`specs/recuperacion-de-contrasena-por-email.md`): both web and mobile send `resetPasswordForEmail` with `redirectTo` pointing at the **web** SPA (`WEB_APP_URL` = `https://www.tribbu.ar/app` in `src/lib/appUrl.js`, consumed by mobile as `@shared/appUrl`) — mobile links deliberately complete in the browser, not via a native deep link. The link lands on `/app` with `#…&type=recovery`; `src/supabase.js` sets `detectSessionInUrl:true` + `flowType:"implicit"` explicitly so that hash is processed, and `App.jsx` renders `<NuevaPasswordRecovery/>` (a full-screen recovery view in `features/auth`, above the login/app branches) on the `PASSWORD_RECOVERY` event or a lazy `type=recovery` hash check. After `updateUser({password})` succeeds it clears the hash and reloads → the persisted session logs the user in with no re-login. **Requires manual Supabase config** (Authentication → URL Configuration): Site URL `https://www.tribbu.ar/app` and Redirect URLs allow-list `https://www.tribbu.ar/app` + `https://www.tribbu.ar/app/**` — without it Supabase ignores `redirectTo` and falls back to the (stale) Site URL.
- **Privileged auth operations** (create user, change another user's email/password, find by email) go through the Edge Function `supabase/functions/manage-auth-user/index.ts`, called via `src/lib/authAdmin.js`. The function verifies the caller's `rol` is `super` or `colegio_admin` via JWT before using the service-role key server-side — never `admin` (a Room Parent is `rol="admin"` too but only for their own curso, and this function's `create`/`update`/`find` actions operate on any user in the system with no curso scoping; letting `admin` through here was a real privilege-escalation bug, fixed 2026-08-25). `colegio_admin` (multi-colegio, 2026-09) is scoped inside the function itself (`targetEnColegio()`): it can only `update`/`find` a user who already belongs to its own `colegio_id` (derived the same way as `es_colegio_admin_de_usuario()` in `supabase/multi-colegio.sql`, resolved by hand since the function runs with the service client, no `auth.uid()`); `create` has no target yet so it's unrestricted for both roles. **Never** add the service key to the frontend — route new admin operations through an Edge Function instead. **`find`/`update` self-heal** (fixed 2026-09-10): `listUsers()` used to be called with no pagination, so with >50 Auth users whoever fell past page 1 silently failed to resolve by email; `find` and `update`'s fallback now page through all of Auth (`findAuthIdByEmail()`). `update` also recovers when the caller's stored `auth_id` no longer exists in Auth (deleted manually, or a leftover from the pre-Auth bcrypt migration) — the client now always sends `current_email` (the user's *current* email, not the new one) alongside `auth_id`; on a `updateUserById` "not found" the function retries via `findAuthIdByEmail(current_email)`, or — if truly no Auth account exists — creates a fresh one with the password being set, returning `auth_id_reparado` for the caller to rewrite `usuarios.auth_id`. Before this, "cambiar contraseña" for such a user failed with a raw "User not found" and no recovery path (`src/features/superadmin/index.jsx`'s `guardarUsuario`/`guardarCuentaEspecial`, mirrored in `mobile/features/superadmin/index.jsx`). The "no existe" check is `error.status === 404`, not a text match on `error.message` — a fuzzy `/not found/i` match briefly misfired on `AuthRetryableFetchError` (a transient 5xx that supabase-js explicitly marks "safe to retry"), wrongly triggering account recreation instead of just retrying; `withRetry()` now retries transient 5xx/`AuthRetryableFetchError` responses (300ms/600ms backoff, 3 tries) on every Auth admin call before giving up. When `auth_id` is missing entirely (not stale — never set), the client now falls back to `authAdminCreate` with the password being set, instead of dead-ending on "No se encontró el usuario en Supabase Auth".
- **`instance_id`/`aud` NULL — root cause of ~58 accounts invisible to Auth (found & fixed 2026-09-11)**: rows inserted directly into `auth.users` by the one-time bcrypt→Auth migration scripts (`migrate_to_auth.cjs`/`migrate_remaining.cjs`) left `instance_id` and `aud` `NULL` instead of `00000000-0000-0000-0000-000000000000`/`"authenticated"` (the columns Supabase Auth's own `admin.createUser()` always fills in, but a raw SQL insert doesn't). Auth filters **every** admin-API query by `instance_id` — a `NULL` never matches, so those accounts were 100% valid rows (right email, right password hash, right `usuario_hijos`/`usuario_cursos`) yet totally invisible to `listUsers`, `getUserById`, `updateUserById`, and the dashboard's own Users list, while still showing up fine in a direct SQL query — the exact "some accounts work, some don't, always the same ones" symptom that made this hard to place (surfaced as "Database error checking email" from `updateUserById`). Fixed with one manual `update auth.users set instance_id = '00000000-0000-0000-0000-000000000000', aud = coalesce(aud,'authenticated'), role = coalesce(role,'authenticated') where instance_id is null or aud is null or role is null;` (ran once against prod, no migration file committed for it). Any account created by directly writing to `auth.users` again (instead of through `admin.createUser`/`auth.signUp`) will reintroduce this — diagnose the same way: compare a working account's `auth.users` row against a broken one's, `instance_id`/`aud` are the columns that matter.
- **`UploadApoderadosExcel` (bulk import, both platforms) silently created apoderados with no Auth account** (fixed 2026-09-11): if `authAdminCreate` threw for a row (rate limits during a big batch are the likely trigger), the error was only `console.error`'d — the `usuarios` row was inserted anyway with `auth_id: null`, and the row still counted toward the "✅ N apoderados procesados correctamente" success count, so a silently-broken account was indistinguishable from a working one until someone tried to log in. Now collects the failed emails into `sinAuth` and appends them to the completion message so the admin knows exactly who to fix.
- **Self-service account deletion** (Apple 5.1.1(v)) — Edge Function `supabase/functions/delete-account/index.ts`: no role required, the caller's JWT is the only account it can delete. Removes the user's own rows (push_tokens, leídos, asistencias, adquiridos, personal recordatorios, usuario_cursos/usuario_hijos, `usuarios` + Auth user), nulls historical refs (colecta_pagos.pagado_por, colectas/cumples responsable_id) and never touches `hijos`; `super` is refused. Mobile UI: "Eliminar mi cuenta" in Más → Cuenta (`mobile/app/(tabs)/mas.jsx` + `deleteMyAccount` in `mobile/lib/authAdmin.js`); web: `EliminarCuentaModal` (`features/auth`), opened from the account actions in both web layouts of `App.jsx`.
- **Push** is sent via the `send-push` Edge Function (`supabase/functions/send-push/index.ts`) called from `src/lib/push.js` (`sendPush`, `getUserIdsByCurso`) — the single source for push helpers, imported by every feature as `../../lib/push`. Requires a real logged-in user's JWT as bearer (no super/admin role check — any apoderado triggers push today, e.g. creating a recordatorio) — `sendPush` sends `session.access_token`, **not** the anon key; calling with just the anon key (no real user) is rejected with 401 (fixed 2026-08-25, was previously callable by anyone holding the — public — anon key, no account needed).

Dedupe via `avisos_automaticos_log` (unique `clave`, inserted before sending; `supabase/avisos-automaticos.sql`). Also in diario: autorizaciones whose `fecha_limite` is tomorrow → "✍️ Falta tu respuesta" to families with an unanswered hijo in that curso. Families can turn each type off in `preferencias_avisos` (`supabase/preferencias-avisos.sql`; no row = all on; UI: web `PreferenciasAvisosModal` from the account menu "🔔 Notificaciones", mobile Más → Notificaciones switches; list of types in `src/lib/avisos.js` / `@shared/avisos`) — only automatic avisos, live pushes always arrive. Sending (Expo API, ticket + background receipt pruning of dead tokens) lives in `supabase/functions/_shared/expoPush.ts` (`enviarPush(sb, [{usuario,title,body,data}])`), shared by `send-push` and `avisos-automaticos` — redeploy both after touching it. `&dry=1` computes without logging/sending and returns a text sample; with dry, `&hoy=AAAA-MM-DD` simulates another day — use that to test, never a real run. Scheduling (pg_cron + pg_net + Vault) lives in `supabase/avisos-automaticos-cron.sql`. New push `type: "resumen"` → Muro in both TAB_MAPs.

The token is generated/regenerated via the RPC `regenerar_calendar_token()` (`supabase/calendar-sync.sql` + `supabase/calendar-token-hardening.sql`, `security definer`, same pattern as `crear_apoderado`/`verificar_codigo`). The feed combines `eventos`, cumpleaños (hijos + maestros), and recordatorios that carry `hora_inicio` (the "citas" with a real schedule — a recordatorio without `hora_inicio` is just a text/aviso and stays out of the calendar); festejos are `eventos` with `tipo="festejo"` and are **visible only to who they concern** (2026-09-23, `supabase/festejos-solo-invitados.sql`): RLS `eventos_select` lets a festejo through only to families with an invited hijo (or invited directly via `evento_asistencia.usuario_id`), the cumpleañero's family (`es_padre_de(alumno_id)`), its creator, and super — since 2026-10-22 (`supabase/festejos-sin-colegio.sql`, aplicado) **not the colegio** (colegio_admin/Secretaría: neither the festejo nor its `evento_asistencia`; the panel's Eventos list also filters them out, web + mobile) — a Room Parent sees it only if one of those applies; every other evento type is still visible to the whole curso. The feed reads with the service role, so it applies the same rule by hand (`leToca`). **Every fetch is logged** on the user's `usuario_calendar_tokens` row (`supabase/calendar-feed-lecturas.sql`, 2026-09-23): `leido_en`/`leido_por` (User-Agent) for any client, plus `google_leido_en` when the UA matches `Google-Calendar-Importer` — the only real proof a Google subscription is working ("Ya lo agregué" just records that the user *thinks* they finished). Both calendar buttons read `google_leido_en` to show "✓ Google Calendar ya está leyendo tu calendario (última vez hace X)" and count as synced; `regenerar_calendar_token()` clears the three columns. Android Google Calendar app gotcha: a URL-subscribed calendar arrives with "Sincronizar" **off** (listed in the app's Settings, missing from the drawer) — the guided steps now include turning it on. The VCALENDAR carries `X-WR-CALNAME:Tribbu` so it doesn't show up in Google/Apple/Outlook under the raw function URL (note: some clients, notably Google Calendar, only read `X-WR-CALNAME` at subscribe time — a calendar added before this existed needs to be removed and re-added to pick up the name). **Google Calendar's polling of a subscribed-by-URL calendar is infrequent and outside our control** (observed: an event's `hora_inicio` edited in the app took well over an hour to show correctly in Google Calendar, still showing the old time in between) — if a user reports "I changed the time/date in the app but Google Calendar still shows the old one," that's expected Google-side caching, not a feed bug; removing and re-adding the subscription sometimes (not reliably) forces an immediate re-fetch. Google Calendar's "Add by URL" (`calendar.google.com/calendar/render?cid=`) specifically requires the `cid` value to use the `webcal://` scheme, not `https://` — the web sync button converts it before opening that link (mobile's iOS `webcal://` open already did). UI: `src/features/calendario/BotonAgregarCalendarioWeb.jsx` (web) and `mobile/features/calendario/BotonAgregarCalendario.jsx` (mobile), both wired into their respective `calendario/index.jsx`. The mobile flows are per-platform (`specs/eleccion-de-calendario-mobile.md`): **iOS** picks Apple Calendar (`webcal://` open) or Google Calendar (`render?cid=` opened via `expo-web-browser`'s SFSafariViewController — universal links don't fire inside it, so the native Google Calendar app can't intercept); **Android** has no working web shortcut at all (`calendar.google.com` is an App Link of the Google Calendar app, which fakes success on `?cid=`; Google also blocks login in embedded WebViews), so mobile shows the **same two-option chooser on both platforms** — "Calendario del dispositivo" vs "Google Calendar" — and each option uses whatever mechanism actually works on that OS (table in the component header). **iOS/dispositivo** = `webcal://` (Apple Calendar subscribes to a native "Tribbu" calendar the server pushes to; strictly better than writing events ourselves, no calendar permission). **Google (both platforms, identical)** = the **guided subscription** described below — iOS used to open `render?cid=` in an SFSafariViewController, dropped 2026-08-28 so the experience matches Android (users who already did it keep `metodo="gcal"`, still counted as synced). **Android/dispositivo** = `expo-calendar` (native module — regenerate `mobile/android/` after (un)installing it) with the engine in `mobile/lib/calendarSync.js`: fetches the same ICS feed, minimal parser for our own generator's format, creates a device-local **"Tribbu" calendar**, UID→deviceEventId map in AsyncStorage, delete-and-recreate on change, removal of events gone from the feed, re-sync on Calendario mount/app foreground throttled to 1/hour, and "Desconectar" deletes the whole calendar. Known and deliberately accepted (2026-08-28): that calendar is `account_type=LOCAL` — visible in Samsung/AOSP calendar apps with its own color/toggle, but **the Google Calendar app does not list or draw third-party LOCAL calendars** (verified in the emulator against a real account: `visible=1`, 108 events, still absent from drawer and grid) and it never reaches calendar.google.com; the option's copy says so and points Google Calendar users to the other option. **Google** = **guided subscription**: the app hands over the feed link ("Copiar enlace" / "Enviármelo por mail" via `mailto:`) plus the 4 steps to add it **once** from `calendar.google.com` on a computer ("Otros calendarios" → + → "Desde URL"), and a "Ya lo agregué" button that persists `metodo="suscripcion"`. That is the only path that yields a real **"Tribbu" calendar inside the Google account** (`ownerAccount …@import.calendar.google.com`, own name/color/toggle, syncs everywhere — verified); creating one from the app would need the Calendar API + OAuth, out of scope, and the phone-side shortcuts all fail (`calendar.google.com` is an App Link the Google Calendar app hijacks with a fake success; embedded WebView login is blocked). `metodo` in AsyncStorage (`calsync_<userId>`) records what the user actually did: `webcal`/`device`/`suscripcion` (+ legacy `gcal`) = synced, `copia` = only copied the link; legacy `google`/`1` are treated as `copia`. **Crash fixed 2026-08-28 in `calendarSync.js`**: cumpleaños (the only all-day + `RRULE:FREQ=YEARLY` VEVENTs) are expanded in the parser to one plain event per year (`ANOS_RECURRENCIA = 3`, UID `<uid>::<año>`) instead of passing `recurrenceRule` — for an all-day recurring event expo-calendar emits `DURATION="PT86400S"`, `CalendarProvider2.fixAllDayTime()` parses it with a naive substring (`Integer.parseInt("T86400")`) → `NumberFormatException` that escapes `saveEventAsync`'s narrow catch and **kills the process**, invisible to any JS try/catch. Timed events may still carry `recurrenceRule`. See `specs/sincronizacion-de-calendario.md` + `specs/eleccion-de-calendario-mobile.md`.

A separate **React Native (Expo, managed)** app living in `mobile/`. It does **not** touch the web app (`src/`) beyond the env/storage-injection refactor described above. See `mobile/README.md` for setup/EAS/backend steps.

## Repository hygiene

The root `*.cjs` scripts (`hash_passwords`, `migrate_to_auth`, `migrate_remaining`, `reset_passwords`, `backup_tribbu`) are **one-time** Node migration/backup utilities that connect to the live project with the service-role key, read from `SUPABASE_SERVICE_ROLE_KEY` in the environment (never hardcoded — run as `SUPABASE_SERVICE_ROLE_KEY=... node <file>.cjs`, a real key was found hardcoded in all five on 2026-08-25; the GitHub repo is **public**. **Legacy JWT API keys (anon + service_role) were disabled on 2026-10-16**, so that leaked key no longer works — the scripts now need a new `sb_secret_…` key, sent only as `apikey` since it is not a JWT; `backup_tribbu.cjs` handles both). Do not run them casually, and do not put a real key back in the file or copy that pattern into `src/`. **`backup_tribbu.cjs` is the exception — it's the ongoing, read-only full backup** (rewritten 2026-09-23): writes `tribbu_backup_<fecha>/` (gitignored) with `data.json` (every `public` table, discovered via PostgREST's OpenAPI and paginated by PK — before, it had a hand-kept list missing newer tables and silently truncated any table over PostgREST's 1000-row cap), `auth_users.json` (id/email/dates — Auth never exposes password hashes) and `storage/<bucket>/…` (every file in `adjuntos`/`eventos`/`libros`; `--sin-archivos` skips it). The service key can be fed without pasting it via the logged-in Supabase CLI: `npx supabase projects api-keys --project-ref gctymjhblvocvaenmdhr -o json`.

**API keys (2026-10-16)**: the project uses only the new keys — legacy `anon`/`service_role` JWT keys are **disabled** (the JWT signing key is ECC; the legacy HS256 secret was revoked the same day). Clients use the publishable key (`sb_publishable_…`: Vercel `VITE_SUPABASE_ANON_KEY`, `mobile/eas.json`, local `.env`s). Edge Functions read their keys through `supabase/functions/_shared/claves.ts` (`CLAVE_SERVICIO`/`CLAVE_PUBLICA`, from the injected `SUPABASE_SECRET_KEYS`/`SUPABASE_PUBLISHABLE_KEYS` JSON) — never `Deno.env.get("SUPABASE_SERVICE_ROLE_KEY")` directly. **All Edge Functions are deployed `--no-verify-jwt`**: the gateway's `verify_jwt` only understands the legacy secret, so send-push/manage-auth-user/delete-account check the caller in code (`auth.getUser()` with the request's Authorization → 401) and the cron/pg_net ones with `x-cron-secret`. Keep that pattern for new functions (deploy with `--no-verify-jwt` + check in code).
